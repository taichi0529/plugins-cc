# 日報を Obsidian に記録する

## 実行時コンテキスト

```!
"${CLAUDE_PLUGIN_ROOT}"/scripts/obsidian-cc.sh context --pull || true
```

- ユーザーからの補足: $ARGUMENTS

**上の出力が唯一の事実源。** パス・日付・ブランチ・既存ノートは会話の文脈から推測せず、必ずこの出力の値を使うこと。以降この文書では次の名前で参照する。

| 名前 | 出力中のキー | 用途 |
| --- | --- | --- |
| `<repoRoot>` | `repoRoot` | git リポジトリルート。すべての git コマンドの `-C` に渡す |
| `<vaultDir>` | `vaultDir` | デイリーノート / プロジェクトノートの置き場 |
| `<today>` | `today` | 今日の日付 (`YYYY-MM-DD`) |
| `<dailyNote>` | `dailyNote` | `<vaultDir>/<today>.md` |
| `<remote>` / `<branch>` | `remote` / `branch` | push 先 |

**このスキルはどのプロジェクトのセッションからでも呼ばれる。** git 操作は必ず `git -C <repoRoot>` を使い、カレントディレクトリのリポジトリには絶対に触れないこと。

---

## 手順

### 0. 設定と同期の確認

コンテキスト出力の 1 行目が `STATUS: ok` でなければ、**何も書かずに終了する**。ユーザーには「`/obsidian-cc:setup` を実行して Obsidian の設定を作ってほしい」と伝え、出力に含まれる問題点をそのまま示す。設定を自分で書きに行かないこと。

次に `pull:` の行を見る。コンテキストを読む前に `<remote>/<branch>` から **fast-forward に限定して**最新化してある（履歴を書き換えないため merge コミットは作らない）。

- `up-to-date` / `fast-forwarded <old>..<new>` → そのまま進む
- `skipped (...)` → 理由をユーザーに伝えてから進む。現在のブランチが設定と違う場合、日報はそのブランチにコミットされることになる
- `failed (...)` → **書き込みに進まず、ユーザーに判断を仰ぐ**。ローカルとリモートが分岐している場合、追記しても push で弾かれる可能性が高い。手動で rebase / merge してもらうか、この回は書かずに終わるかを選ばせる

さらに「未 push のコミット」が列挙されている場合、**日報を push するとそれらも一緒に送られる**。手順 3 のドラフト提示でその事実を明示し、ユーザーが承認の判断に使えるようにすること。

### 1. 作業内容の収集（本体セッションで実行）

現在のセッションの会話から、今日行った作業を抽出する。補足が渡されていればそれも併合する。

会話に記録すべき作業実績が無い場合は、**何も書かずにその旨を伝えて終了する**。空の日報を作らない。

### 2. プロジェクトの特定

コンテキスト出力の「existing project notes」と照合し、該当するものを `[[名前]]` 形式のリンクにする。該当が無ければ無理にプロジェクトノートを新規作成しない。

### 3. ドラフト提示と確認（本体セッションで実行）

以下を提示する。

- デイリーノートへの追記内容
- 各プロジェクトノートへの追記内容
- 既存の表・チェックボックスの更新が必要と判断した場合は、その提案（勝手に適用しない）

提示したうえで `AskUserQuestion` を使い、**1 回だけ**確認を取る。ここが唯一の歯止めになる。

承認されなければ何も書かずに終了する。

### 4. 書き込み・commit・push（サブエージェントに委譲）

承認後、`Agent` tool で以下を指定してサブエージェントを起動する。

- `model`: `"opus"`
- `run_in_background`: `false`（結果を待って報告するため必須）
- `description`: `"Obsidian 日報の書き込みと push"`

プロンプトには**承認済みのドラフト全文**と、下の「書き込み規約」「禁止事項」を丸ごと埋め込む。`<repoRoot>` などのプレースホルダは**実際の値に展開してから**渡すこと（サブエージェントはこのコンテキスト出力を見ていない）。判断は本体で終わっているので、サブエージェントは機械的な適用に徹させる。

サブエージェントには次を報告させる。検証コマンドは**この通りに指定する**こと。

- 変更したファイルの一覧
- commit hash と `git -C <repoRoot> show --stat HEAD`（意図しないファイルの混入がないこと）
- pre-commit フック（gitleaks 等）の結果
- push の**直前**に実行した `git -C <repoRoot> log --oneline <remote>/<branch>..HEAD` の出力。自分が作った日報のコミット以外が含まれていたら、それも push で一緒に送られる。push は止めなくてよいが、**便乗して送られたコミットを必ず報告する**（承認から実行までの間に別セッションがコミットしている場合がある）
- push の可否（`git -C <repoRoot> status -sb` の出力）
- `git -C <repoRoot> diff HEAD~1 HEAD --numstat`（追記のみで削除が 0 行であること）

`diff HEAD~1 HEAD` の **`HEAD` を省略しないこと**。省略すると HEAD~1 と**ワーキングツリー**の比較になり、コミットに含まれない未コミット変更まで差分に混ざって誤報の原因になる。vault の最初のコミットで `HEAD~1` が無い場合は、この行を飛ばして `show --stat HEAD` だけで確認する。

作業ツリーに無関係な未コミット変更がある場合は、**それらを一切 `git add` しないよう明示し**、実行後も残っていることを `git -C <repoRoot> status --short` で確認させる。

### 5. 結果報告

サブエージェントの返答をユーザーに報告する。失敗した項目があれば隠さずそのまま伝える。

## 書き込み規約

### デイリーノート

ファイル名は `<today>.md`（`YYYY-MM-DD.md`）で**固定**。Obsidian 側の Bases（`日報.base` 等）がファイル名の正規表現 `/^\d{4}-\d{2}-\d{2}$/` で日報を拾っている前提なので、命名を変えると一覧から落ちる。

- 既に存在する場合は**追記**する。上書きしない
- 存在しない場合は frontmatter 付きで新規作成する

```markdown
---
tags:
  - daily
projects:
  - "[[ProjectName]]"
---

## 今日やったこと

- ...
```

- `projects` は既存の値を保持したうえでマージする
- 本文は `## 今日やったこと` 配下に箇条書きを追加する。見出しが無ければ作る

### プロジェクトノート

**追記のみ。既存行の書き換えは禁止。**

- 該当する `### <トピック>` 見出しの配下に `- <today>: <内容>（[[<today>]]）` を追加する
- 該当する見出しが無ければ `## トピック` 配下に新しい `###` を作る
- 手書きの表・callout・チェックボックスには触れない
- それらの更新が必要な場合は手順 3 で提案し、承認された分だけ適用する

### commit / push

**すべての git コマンドに例外なく `-C <repoRoot>` を付けること。** カレントディレクトリがどこであっても正しいリポジトリに向くようにするため。`cd` してから実行する方式は禁止（このスキルは別プロジェクトのセッションから呼ばれるため、`-C` を落とすと他人のリポジトリにコミットする）。

```bash
git -C <repoRoot> add <触ったファイルのみ>
git -C <repoRoot> push <remote> <branch>
```

commit メッセージは日本語で、その日の作業内容が分かる 1 行 + 必要なら箇条書き。複数行のメッセージをヒアドキュメントで渡す場合も `-C` を落とさないこと。正しい形は次の通り。

```bash
git -C <repoRoot> commit -m "$(cat <<'EOF'
add: <today> の日報を更新

Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>
EOF
)"
```

実行前に `git -C <repoRoot> rev-parse --show-toplevel` の出力が `<repoRoot>` と一致することを確認すること。

## 禁止事項

- `git commit --no-verify` の使用。vault リポジトリに pre-commit フック（gitleaks 等）がある場合、**検出されたら握り潰さず、理由を報告して中断する**
- カレントディレクトリのリポジトリへの git 操作。`-C` を省略した git コマンド、および `cd` による移動
- `git add -A` / `git add .`（無関係な変更を巻き込むため、触ったファイルだけを add する）
- `<vaultDir>` の外への書き込み
- 会話に根拠のない内容の創作。不明な点は `> [!todo] 未記入` の callout として残す
- デイリーノート・プロジェクトノートの既存内容の削除や上書き
